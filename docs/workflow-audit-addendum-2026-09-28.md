# Scout workflow and complexity audit addendum

**Audited source:** `c3bea6a` (`scout-v15`), as used for the [independent architecture audit](architectural-audit-2026-09-28-independent.md). This continuation follows each production step and the study/evaluation path. It reviews duplication and removable complexity, without changing behavior, calling providers, or writing to the study database. Findings in the first report remain in force; this document adds details and new findings rather than repeating its entire argument.

## Immediate conclusions

1. **The study ceiling has a spec-level escape hatch.** `StudySpec.Arm.args` accepts an extra `--max-usd` after the runner's cap. Argparse takes the last value. An offline probe produced an effective $99 cap from a planned $0.25 cap. No checked-in spec currently uses that override, so this is a latent, reproducible integrity defect, not evidence that a past study overspent.
2. **A planner failure can be invisible in the delivered report and durable record.** Auto depth becomes `standard`, coverage disappears, and a later successful scout/synthesis can make the run `complete`. The explanatory note lives only in the in-memory `ScoutRun.notes` and optional output JSON; the renderer does not show it and Postgres has no `notes` field.
3. **Follow-up coverage is asserted by control flow.** Every untagged claim from a deep dive is assigned the gap's `coverage_id`, even if the claim is incidental. The fuzz oracle currently requires this assignment, so a semantically wrong coverage mark can pass the invariant suite.
4. **The largest simplification is one canonical observation and one canonical reader artifact.** Tool returns are parsed twice into evidence text and source records, while grading, support audit, diagnosis, rendering, and quality assessment use different report projections. Joining those at the data boundary removes duplication and closes correctness gaps. Deleting the offline harness, reading fallbacks, or separate evaluation questions would remove useful behavior rather than bloat.

## New findings and offline evidence

### W01 — P1: a study arm can override the parent ceiling

`StudySpec.Arm.args` is an unrestricted list (`study.py:89-94`). `command` puts protected flags `--study`, `--arm`, `--replicate`, `--max-usd`, and `--out` into `labels`, then appends the arm's arguments (`study.py:279-291`). CLI argparse accepts repeated options and uses the last value (`cli.py:625-665`). `StudySpec._targets` validates only target shape, model flag presence for reruns, and unique arm names (`study.py:120-137`).

**Offline probe:** A `rescout` spec with a $1 per-run cap, a generated $0.25 remaining-room cap, and arm arguments `--model openai:gpt-6-luna@low --max-usd 99.00 --out /tmp/diverted` produced a command containing both caps and both output paths. Argparse resolved `max_usd=99.00` and `out=/tmp/diverted`. No provider call was made. The later path also prevents the parent from finding its expected `run.json`, so it conservatively charges only the *planned* $0.25 cap even though the child could dispatch under $99. A duplicate `--case` or `--model` could likewise make the actual arm differ from the preflighted/planned one. The checked-in `studies/*.toml` files contain no such protected duplicate flags.

**Repair:** Reject protected flags in `Arm.args` at spec load, including both `--name value` and `--name=value` forms, before preflight or any spend. Prefer parsing the remaining role-specific arguments once and constructing child arguments from typed fields, with parent-owned flags appended last as defense in depth. Test duplicate cap, output, case/model and study labels, including cheap mode. Record the effective argv and spec digest in the run or study artifact. This is a correction to the study safety boundary, so update `BUDGET_POLICY_VERSION` and study documentation when implementing it.

### W02 — P2: planner fallback can be labelled complete without a visible explanation

`_Run._plan` catches expected failures, appends a note, and creates `ResearchPlan(questions=[q1], depth=asked or "standard")` (`scout.py:515-550`). The run then continues. If its one scout and synthesis return, `_status` can be `complete` (`scout.py:1006-1013`). The note appears in the optional JSON artifact produced from `ScoutRun.to_record()` (`scout.py:282-295`), but `render_markdown` never prints `record.notes` (`render.py:18-75`). `RunStore.finish_run` has no notes field (`store.py:87-107`), and `research show` reconstructs no notes (`cli.py:29-35`).

This is a useful availability fallback, but the user sees neither the failed planning nor the narrower automatically chosen depth in the report. A `complete` run therefore does not imply the intended broad/deep workflow executed. The study runner's summary is also based on status and checks, not this note.

**Repair:** Add a structured planning outcome to run checks/config and the durable row, surface it under “Needs review,” and mark the run `partial` or use a separate `degraded` dimension when planned scope was lost. Preserve explicit user depth. An offline scripted planner failure followed by a successful scout/synthesis should assert the stored and rendered warning; it need not call a provider.

### W03 — P2: follow-up claims inherit a coverage verdict they did not earn

`_Run._deep_dive` gives any claim with no `covers` the gap's `coverage_id` (`scout.py:705-712`). `coverage_states` counts any tagged claim as `covered` (`evidence.py:468-491`), even if its evidence is thin or the statement concerns another topic. Thus one irrelevant but otherwise valid claim can make the gap look closed. The dry-run invariant explicitly complains if a targeted dive leaves any claim untagged (`dryrun.py:780-791`), so the harness reinforces this behavior instead of acting as an independent oracle.

**Repair:** Do not tag unmarked claims on behalf of the model. Keep the gap target separate from claim coverage; derive coverage from supported claim content or require a focused evidence-to-requirement mapping with a validator. Add a negative test: a dive that searches a gap but returns only an incidental claim must leave that item open. Change the workflow/evidence version if stored coverage semantics change.

### W04 — P2: one document can become multiple numbered sources

`_source_key` serializes the complete model-written `SourceRef`, including title and status (`evidence.py:379-381`). `source_table` numbers those keys (`evidence.py:311-335`). An offline probe with two claims citing the same `https://example.org/paper` but titles “Paper” and “Paper: revised title” produced two source rows, `s1` and `s2`, with the same URL. This inflates source counts, duplicates synthesis context, and can make the answer appear better sourced than it is. It also interacts with the identity-matching weaknesses in A07.

**Repair:** Give one work a canonical, code-owned ID based on a checked URL/DOI/arXiv identity plus work-version rules, while storing each model-written metadata variant as an assertion to resolve against tool records. Do not merge preprint and published versions merely because one cites the other's DOI. Test same URL/different title, distinct query-selected documents, and preprint/published copies.

### W05 — P2: prompt fingerprint omits model-visible workflow text

`prompt_fingerprint` hashes `prompts.INSTRUCTIONS`, role output schemas, budget notes, and two history notes (`prompts.py:117-133`). It does not hash the JSON prompt builders in `_Run._plan`, `_scout`, `_analyze_gap`, or `_synthesize`, including `_scout`'s literal “Investigate this gap. Cite only sources returned by your own tools.” (`scout.py:530-736`). A change to those fields or literal text can leave the fingerprint unchanged if a developer forgets to bump a workflow version. The git commit helps only when the code was committed and available; it is not a content fingerprint of the actual prompt.

**Repair:** Centralize model-visible prompt templates/payload construction near `prompts.py` and hash them as part of a manifest, or record a digest of the exact instructions, schema, and runtime prompt per call. Keep question text out of a global fingerprint and in a separate input hash. Test that changing every model-visible static string changes the fingerprint. This preserves the existing owner boundaries: agents still own prompt semantics, `scout.py` still chooses when calls occur.

### W06 — P2: the study's effective design is not recorded as one immutable artifact

The study runner freezes role models and model-call limits from one `Settings()` snapshot (`study.py:471-481`), which is good. It writes per-run study ID, arm and replicate, and a run config. It does not store a canonical hash or copy of `StudySpec` with the decision rule and arm arguments. The TOML can change later; reruns named with the same study label can then refer to different designs. Historical `git_commit` on each run is helpful but does not capture uncommitted spec edits or the exact parent command line. W01 shows why effective argv matters.

**Repair:** At study start, save immutable `spec.json`/digest, resolved arm environments with secrets redacted, effective child argv, source-run hashes, and decision-rule text in the output directory and run metadata. Reject a reused study label with a different digest unless explicitly resumed as a new revision. This is provenance work, not another database service.

### W07 — P3: chained search hides result provenance

`SearchChain.search` returns the first nonempty `WebSearch.search` result verbatim (`web.py:226-252`). That result has titles, URLs and snippets, but no engine name (`web.py:185-214`). Cache counts and paid search charges report totals, yet the scout transcript and ledger cannot show which engine supplied a particular result in a chain. For standalone-engine studies this is immaterial; for hybrid chains and fallback design it weakens cost/efficacy attribution.

**Repair:** Include `engine` or `via` on the tool return/result and retain it in observations/outcomes. The model need not use the field to decide what a source says. Keep per-engine success and cost metrics in the study summary.

### W08 — P3: `content_sha256` names two different byte streams

The native fetcher hashes the original HTTP response bytes (`web.py:386`); fallback readers construct `_document` by hashing extracted UTF-8 text (`reading.py:104-106`). `WebAcquisition._window` exposes both under `content_sha256` (`web.py:341-350`). No current decision in the inspected source uses this field, so there is no demonstrated false grade or budget error. It is nevertheless unsafe to use as a cross-reader content identity or deduplication key.

**Repair:** Rename it to `response_sha256` where raw bytes exist and add `extracted_text_sha256` for all readers, or standardize the latter with a version bump. Keep both only if their purposes are explicit.

## Duplication and complexity inventory

The production package is roughly 10,000 lines of Python; size alone is not evidence that a component is unnecessary. This inventory separates **duplicate policy/representation** from **legitimate adapters and test machinery**.

| Area | Duplication or weight | Lean change with low architectural risk | What to preserve |
|---|---|---|---|
| D01 Tool-return parsing | `tools.labeled_texts` and `source_records` independently branch over web, fetch and scholarly returns (`tools.py:152-212`); `tool_outcomes` parses them a third time. | Parse each tool return once into a typed observation carrying identity, text/access, metadata, origin, cost and outcome; project the three current views from it. Test parity on stored transcripts. | Keep the raw transcript for audit and replay; do not give the scout ledger ownership. |
| D02 Reader projections | Renderer, rubric `reader_text`, quality input, support auditor, and diagnosis each assemble a different text surface (`render.py`, `evals.py:143-161`, `quality.py:132-137`, `audit.py:72-90`, `diagnose.py:52-78`). | Define one versioned reader artifact and assertion map; feed projections from that artifact. | D03 Study subprocesses | `_invoke`, `_invoke_output`, and `_preflight` construct related subprocess calls; grade/audit/diagnose parse printed lines (`study.py:341-435`). | One supervised child runner with signal forwarding, bounded wait, typed JSON result and stderr for diagnostics. | Keep subprocess isolation for old git-ref arms and failure containment. |
| D04 Evaluation records | `GradeRecord`, `QualityRecord`, `AuditRecord` repeat usage/cost/error/message fields and their row serializers; `store.py:245-322` repeats insert scaffolding. | Extract a small shared serialization/insert helper for common fields; leave versioned verdict schemas explicit. | Never collapse distinct evaluator versions or questions. |

| D06 Model wrappers | `request`/`request_stream` branches repeat reserve, retry and settlement in `rate_limit.py:255-314` and `study_budget.py:148-185`. | Share error classification, backoff and reservation bookkeeping; leave stream restart rules visibly separate. | Never retry a stream after it has been yielded, or release an uncertain charged request. |
| D07 Configuration recording | `sent_settings()` builds a complete provider model solely to call `prepare_request`; `run_config` calls it for each role and fallback (`models.py:55-63`, `scout.py:319-345`). | Derive the sent-setting snapshot without constructing throwaway HTTP clients, or reuse the actual models. Measure object creation before claiming a resource leak. | Record actual prepared provider settings, not a hand-written guess. |
| D08 Optional features | `history.py` retains trim logic even though current default is off; `SearchChain` and multiple readers add modes (`config.py`, `web.py`, `reading.py`). | Keep behind explicit configuration while studies need them; remove a path only after its experiment ends and no user workflow depends on it. | Historical reruns and documented recovery benefits. |
| D09 Offline harness | `dryrun.py` is about 1,050 lines; much of it is an offline world and fault injector, not production-path weight. Some invariants recompute with production helpers and thus cannot challenge those helpers' semantics. | Split world, fault model and independent oracles for maintainability; add negative semantic cases (W03). Do not delete it or merely mirror implementation. | Seeded deterministic bugs, fault coverage, and no-network tests. |

**Avoid a broad rewrite.** The first cleanup should fix W01 and D03's child contract, then D01 and D02 because those remove duplicate interpretations that currently cause wrong marks. D04-D07 are small follow-up refactors after regression tests. Extracting every long function into another file without reducing policies, representations, or failure states would not improve this architecture.

## Repair order and verification

1. **Study guard:** reject protected arm flags before any preflight, store effective argv/spec digest, and add a cheap/dry regression for duplicate `--max-usd`. This closes a real cap bypass before more paid runs. Bump the budget policy version and document the changed study contract.
2. **Degraded planning and follow-up truth:** persist and render planner fallback state; remove automatic deep-dive coverage tagging; add negative offline tests. Bump workflow/evidence versions when these behaviors change.
3. **Canonical observations and reader artifact:** merge duplicate tool-return parsing, canonicalize source identity without merging distinct works, and align rendered assertions with support and evaluation. Preserve the historical grader as a separate version.
4. **Operational cleanup:** supervise the child process, structure its result, and keep completed call outputs through storage faults. Port the separate signal fix only after reviewing its branch differences; reconcile known abandoned rows separately from this document review.
5. **Measure bloat removals:** collect usage of trimming, search chains and each reader from stored runs, then retire paths with no user or study need. Keep the offline harness and the distinct evaluators.

No paid validation is needed to reproduce W01 or W04. The tests already run for the first report remain the baseline for this unchanged source; this addendum adds documentation and offline probes only. The proposed fixes require their own narrow tests, then the repository's full offline suite and CI.
